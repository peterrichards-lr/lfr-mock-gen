# lfr-mock-gen

[![GitHub Release](https://img.shields.io/github/v/release/peterrichards-lr/lfr-mock-gen)](https://github.com/peterrichards-lr/lfr-mock-gen/releases)
[![License](https://img.shields.io/github/license/peterrichards-lr/lfr-mock-gen)](LICENSE)
[![Rust CI](https://github.com/peterrichards-lr/lfr-mock-gen/actions/workflows/rust.yml/badge.svg)](https://github.com/peterrichards-lr/lfr-mock-gen/actions/workflows/rust.yml)

`lfr-mock-gen` is a Rust CLI that fills a Liferay site with realistic mock Web Content generated by Google's Gemini AI. It reads one of the site's content structures, asks Gemini for entries that match it, validates them, and creates them through Liferay's Headless Delivery REST API, so there is no need for `.lar` imports or Groovy scripts.

## Features

- **Any content structure:** Looks up a structure by ID or name and builds a JSON Schema from its fields, so the generated entries match your own structures rather than a fixed template.
- **Field-aware generation:** Handles text, rich text (HTML), numeric, date, boolean, image, color, select and multiselect fields. Image fields get `picsum.photos` placeholder URLs.
- **Validated output:** Each Gemini entry is checked against the schema; invalid entries are skipped instead of being sent to Liferay.
- **Tone and purpose:** Steer the content with `--tone` (e.g. professional, casual) and `--purpose` (e.g. Blog, FAQ, News, Events).
- **Easy to find and clean up:** Every created article is tagged with the keyword `ai-generated`.
- **Cross-platform:** Pre-built binaries for macOS (Apple Silicon and Intel), Linux and Windows.

## Prerequisites

1. **Rust and Cargo** (only to build from source): the latest stable toolchain.
2. **Gemini API key:** a free key from [Google AI Studio](https://aistudio.google.com/).
3. **Liferay DXP/CE:** a running Liferay 7.3+ instance with the Headless Delivery APIs, and a user who can create Web Content in the target site.

## Installation

### Homebrew (macOS / Linux)

```bash
brew tap peterrichards-lr/tap
brew install lfr-mock-gen
```

### Scoop (Windows)

```powershell
scoop bucket add peterrichards-lr https://github.com/peterrichards-lr/scoop-bucket
scoop install lfr-mock-gen
```

Homebrew and Scoop build from source, which avoids "Unidentified Developer" warnings on macOS and gives a user-level installation on Windows.

### WSL

Install [Homebrew on Linux](https://docs.brew.sh/Homebrew-on-Linux) inside your WSL distribution, then run the Homebrew commands above.

### Manual download

Download the archive for your platform from the [Releases page](https://github.com/peterrichards-lr/lfr-mock-gen/releases), extract it, and put the `lfr-mock-gen` binary on your `PATH`.

### Build from source

```bash
git clone https://github.com/peterrichards-lr/lfr-mock-gen.git
cd lfr-mock-gen
cargo install --path .
```

Check the installation with:

```bash
lfr-mock-gen --version
```

## Usage

```bash
lfr-mock-gen --help
lfr-mock-gen <COMMAND> --help
```

| Command | Description |
| :--- | :--- |
| `data` | Generate mock Web Content with Gemini and create it in a Liferay site. |
| `env` | Report the Liferay project found from the current directory. |

Global options: `-h, --help` and `-V, --version`.

### `data`: generate mock content

```bash
export GEMINI_API_KEY="your-gemini-api-key"

lfr-mock-gen data \
  --api-env GEMINI_API_KEY \
  --liferay-url http://localhost:8080 \
  --liferay-user test@liferay.com \
  --liferay-pass "$LIFERAY_PASSWORD" \
  --group-id 20117 \
  --structure-id "Basic Web Content" \
  --tone casual \
  --purpose News
```

| Option | Required | Description |
| :--- | :--- | :--- |
| `--api-env <NAME>` | Yes | Name of the environment variable that holds your Gemini API key (not the key itself). |
| `--liferay-url <URL>` | Yes | Liferay base URL, e.g. `http://localhost:8080`. |
| `--liferay-user <USER>` | Yes | Username for HTTP Basic authentication, e.g. `test@liferay.com`. |
| `--liferay-pass <PASSWORD>` | Yes | Password for HTTP Basic authentication. |
| `--group-id <ID>` | Yes | Site ID (`groupId`) to create the content in. |
| `--structure-id <ID or NAME>` | Yes | Content structure to generate entries for, matched against the structure's ID or its exact name. |
| `--tone <TONE>` | No | Tone of the generated content. Default: `professional`. |
| `--purpose <PURPOSE>` | No | Kind of content, e.g. Blog, FAQ, News, Events. Default: `Blog`. |
| `--force` | No | Accepted but currently has no effect. |

**What a run does:**

1. Lists the site's content structures (`/o/headless-delivery/v1.0/sites/{groupId}/content-structures`) and picks the one whose ID or name matches `--structure-id`. The run stops if none matches.
2. Turns the structure's fields into a JSON Schema (plus `title` and `description`).
3. Asks Gemini (`gemini-2.0-flash`) for **5** entries that follow the schema, using `--tone` and `--purpose`.
4. Validates each entry and creates the valid ones as structured content (`/o/headless-delivery/v1.0/sites/{groupId}/structured-contents`) with the keyword `ai-generated`. Entries that fail validation or are rejected by Liferay are reported and skipped.

Run the command again to create more entries.

**Credentials:**

- The Gemini API key is read from the environment variable named by `--api-env`, so the key never appears on the command line. The run fails if that variable isn't set.
- Liferay credentials are passed as `--liferay-user` and `--liferay-pass` and sent with HTTP Basic authentication. To keep the password out of your shell history, read it from an environment variable as in the example above.

### `env`: inspect the local Liferay project

```bash
lfr-mock-gen env [--target <TARGET>]
```

Searches upwards from the current directory for a Liferay project (a Liferay Workspace, a Liferay Cloud repository or a client extension) and prints its root, project type, Liferay version (from `liferay.workspace.product` in `gradle.properties`) and the Tomcat directory under `bundles`, when found. `--target` is echoed in the output but doesn't change what is checked. This command doesn't contact Liferay or Gemini.

## Releasing

1. Bump `version` in `Cargo.toml` and run `cargo build` to update `Cargo.lock`.
2. Move the `[Unreleased]` entries in `CHANGELOG.md` into a new `## [x.y.z] - YYYY-MM-DD` section.
3. Commit, then create an annotated tag and push it:
   ```bash
   python3 scripts/release.py --tag vX.Y.Z
   git push origin vX.Y.Z
   ```
   The release workflow fails if the tag isn't annotated, doesn't match `Cargo.toml`, or has no `CHANGELOG.md` section.
4. Update the distribution channels. The Gemini prompt in `.gemini/prompts/update-distribution-channels.md` updates the Homebrew tap from `formula.rb.example` (and, for a first release, the Scoop bucket from `scoop.json.example`):
   ```bash
   "Please execute the steps in .gemini/prompts/update-distribution-channels.md to update my distribution repositories"
   ```
   The Scoop bucket picks up later releases automatically once a tool's manifest exists.

For development, enable the shared pre-commit hook (it runs `scripts/doctor.py`, `cargo fmt` and `cargo clippy`) with `git config core.hooksPath .githooks`, and run the checks by hand with `cargo lint` and `cargo fmt-check`.
